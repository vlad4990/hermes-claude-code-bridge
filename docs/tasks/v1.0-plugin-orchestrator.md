# Orchestrator brief: deliver v1.0 (`docs/tasks/v1.0-plugin.md`) as a pull request

You are the **orchestrator** for this task. You run in Claude Code inside the repository
`~/Projects/hermes-claude-code-bridge` on the owner's machine (macOS, Hermes Agent v0.21.0 installed at
`~/.hermes/hermes-agent`, Claude Code, tmux, a running Telegram gateway). The owner is available in this
session for the few steps that need a human (tapping Telegram buttons, approving a push).

Your deliverable is **one pull request into `main`** from branch `feat/v1.0-plugin` that implements every
section of `docs/tasks/v1.0-plugin.md` (the *spec* below), with the acceptance evidence of spec §5 in the
PR body. Quality over speed: the plugin will be installed by other people.

## Your operating rules

1. **You do not write code yourself.** Every file change, every test run, every log read is done by a
   subagent (Agent tool). Your context is the scarce resource: keep it for decisions, contracts and
   integration. Never `cat` or Read a source file longer than ~60 lines yourself — ask a subagent for the
   specific answer instead.
2. **Every subagent brief is self-contained.** A subagent has no memory of this conversation. Its prompt
   must contain: the repo path, the branch, the exact spec sections it implements (copy the text, do not
   say "see §4.3"), the interface contract it must honour (§ "Interfaces" file), the files it may touch,
   the files it must not touch, the tests it must add/run, and the report format.
3. **Reports are short and structured.** Require every subagent to end with a report of at most ~300
   words in this shape: `Files changed` (paths only) · `Tests` (command + pass/fail counts) · `Deviations
   from the brief` · `Open issues / questions` · `Facts verified against Hermes source` (file:line). Reject
   file dumps.
4. **One writer per file at a time.** Parallel subagents may run only when their file sets are disjoint.
   State the file ownership in each brief.
5. **Adversarial review before integration.** No module lands without a review pass by a different
   subagent that tries to break it (see Phase 4). Findings are verified, then fixed by the original
   implementer or a fresh one; not silently ignored.
6. **Do not touch `~/.hermes/config.yaml`, `~/.hermes/.env`, `~/.claude/settings.json`** except through
   `install.sh`. Gateway restarts (`hermes gateway restart`) are allowed and expected. Never run
   `claude --dangerously-skip-permissions`. Never auto-answer questions or permissions from code.
7. **Commits go on the feature branch only.** Small, per-phase commits with clear messages. Push and open
   the PR at the end (Phase 6) — ask the owner once before the first push.
8. If a spec fact (§1/§2 of the spec) contradicts the Hermes source, the code wins: record the correction in
   `docs/DESIGN.md` decisions log (with file:line) and adapt the design; tell the owner in the final report.
9. When you need the owner (button taps, an ambiguity that changes the design), ask a precise question and
   wait. Do not ask for permission to do routine work.

## Phase 4 — adversarial review (parallel)

Three reviewers in one message, each with a fresh context and this instruction: *"Assume the code is
broken. Find concrete failure scenarios (inputs/state → wrong behaviour), verify each by reading the code
or writing a failing test, report only confirmed findings ranked by severity, with file:line."*

- R1 (fable): `telegram.py` + `inbox.py` — races between poller and callbacks, reconnect double-poller,
  unauthorized taps, stale requests, Telegram message length limits, exceptions escaping into PTB.
- R2 (opus): `runner.py`, `tools.py`, `command.py`, `render.py` — argument injection into subprocess argv,
  encoding, `callback_data` bytes, truncation, error mapping, tool schemas valid JSON-schema.
- R3 (opus): `install.sh`, `plugin.yaml`, `__init__.py`, packaging, docs consistency with the code
  (every command in README/plugin.md actually exists and its flags are real).

For every confirmed finding spawn a fix subagent (same model tier as the original implementer) with the
finding text; re-run the affected tests; commit `v1.0: review fixes`. Findings you decide not to fix go
into the PR body under "Known limitations" with the reason.

## Context hygiene checklist (re-read before each phase)

- Am I about to read a file a subagent could summarise? → delegate.
- Does the brief contain everything the subagent needs without this conversation? → copy the spec text in.
- Did I fix file ownership for parallel agents? → list "owns" and "must not touch".
- Did I require the ~300-word structured report? → yes, every time.
- Is there an unverified claim from a subagent that matters (a Hermes API shape, a passing test)? → ask
  a Haiku subagent to verify it with the concrete command, don't trust the prose.
