## 0. Goal

Today the bridge works through the Hermes **webhook adapter**: `ccb` posts `ask`/`notify` events, `ccb-notify`
delivers text, `ccb-ask` runs an agent turn that rephrases the question, and the human's reply is relayed by the
chat agent to `ccb answer` (3–5 LLM calls per answer). v1.0 adds a **native Hermes plugin** that removes the LLM
from the hot path:

- `ask` events are rendered as Telegram messages with **inline buttons**; a tap runs `ccb answer` directly
  (zero LLM calls). Free text still works (reply to the message, or through the chat agent).
- `notify` events are delivered as plain text by the plugin (no webhook adapter, no HMAC, no filter script).
- The model gets **typed tools** `cc_start / cc_answer / cc_send / cc_status` instead of shelling out to `ccb`.
- `/ccb` slash command for humans.
- Installation: `hermes plugins install vlad4990/hermes-claude-code-bridge` + one bootstrap command.

The skill path (webhook) **stays supported unchanged**; the plugin is the recommended path. Both consume the
same `ccb` CLI and the same event contract. `ccb.py` and `ccb_screen.py` are not modified by this task except
where explicitly listed in §4.7.

## 4. Specification

### 4.1 `plugin.yaml` and `register(ctx)`

```yaml
name: cc-bridge
version: 1.0.0
description: Claude Code sessions in tmux, driven from Telegram — questions and permissions as inline buttons, typed tools for the model.
author: <owner>
license: MIT
homepage: https://github.com/vlad4990/hermes-claude-code-bridge
tags: [claude-code, tmux, coding-agent, telegram, bridge]
kind: standalone
manifest_version: 2
provides_tools: [cc_start, cc_answer, cc_send, cc_status]
provides_hooks: []
config_schema:
  chat_id:        {type: str,  default: "",  description: "Telegram chat that receives events; empty = platform home channel"}
  thread_id:      {type: str,  default: "",  description: "Telegram topic id inside chat_id (optional)"}
  poll_interval:  {type: float, default: 1.0, description: "Inbox poll period in seconds"}
  ccb_path:       {type: str,  default: "",  description: "Path to ccb.py; empty = bundled skills/cc-bridge/scripts/ccb.py"}
  default_cwd:    {type: str,  default: "~/work", description: "Working directory for cc_start when the human gives none"}
```

`register(ctx)`:
1. `ctx.register_tool(...)` ×4 from `tools.py` (toolset `ccb`, `check_fn` = runner can locate `ccb.py` and `tmux`).
2. `ctx.register_command("ccb", handler, description, args_hint="start|status|answer|send|stop …")`.
3. `ctx.register_telegram_handler(telegram.make_factory(ctx))`.
4. `ctx.register_system_prompt_section("cc-bridge.rules", <≤ 900 chars>)`: the four hard rules of
   `SKILL.md` condensed (only the human answers Claude; after `cc_start` the turn is over, do not poll; a
   human reply while a request is pending is the answer → `cc_answer`; never run `claude`/`tmux` yourself).
5. `ctx.register_skill("cc-bridge", <repo>/skills/cc-bridge/SKILL.md, description)` — opt-in reference only;
   document that the full skill is still installed with `hermes skills install` if the user wants the terminal
   procedure in the prompt.

`hermes plugins doctor . --ci` must pass; keep `provides_tools` in sync with the registrations.

### 4.2 `runner.py`

- Resolve `ccb.py`: `ctx.get_config("ccb_path")` → else `<plugin dir>/skills/cc-bridge/scripts/ccb.py` → else
  `shutil.which("ccb")`. Run with `sys.executable`? **No** — the venv python is fine but `ccb.py` is 3.9-safe;
  use `[python3, ccb.py, …]` with `python3` from PATH (same interpreter Claude Code hooks use) so state dirs and
  config resolve identically.
- `run(args, timeout=30) -> (rc, stdout, stderr)`; `status(name=None) -> dict|list|None` via `--json`;
  `answer(name, replies|q_replies, message=None) -> (ok, text)`; `start`, `send`, `stop`, `list`.
- Never raise into PTB handlers: return `(False, "ccb: …")` and let the caller show it.
- All blocking subprocess calls from async code go through `asyncio.to_thread`.

### 4.3 Telegram factory (`telegram.py`, `inbox.py`, `render.py`)

**Target chat.** `chat_id = ctx.get_config("chat_id") or adapter.config.home_channel.chat_id`; `thread_id`
likewise. If neither exists, log a warning once and keep polling (events stay in the inbox) — do not crash.

**Poller** (`inbox.py`): started with `asyncio.get_running_loop().create_task(...)` inside the factory; the task
ends when it is cancelled or when `application.running` turns false after connect (poll that flag each
iteration; `post_shutdown` cannot be attached to an already-built PTB `Application`). One task per adapter
instance: keep the task handle on the adapter object (`adapter._ccb_poller`) and cancel the previous one when
the factory runs again on reconnect. Loop every `poll_interval`:
`sorted(inbox_dir.glob("*.json"), key=mtime)`; read each file; skip files whose mtime < 1 s ago only if the JSON
is incomplete (writer race); dispatch; delete the file **after** a successful send (on send failure keep it
and retry with backoff, max 5 attempts, then move to `<inbox_dir>/failed/`). Dedupe on `event_id` within the
process. Ignore `schema != 1`.

**Stale check for `ask`**: `runner.status(name)`; if `pending is None` or `pending.id != request_id`, drop the
event silently (same rule as `ccb-filter.py`). Also drop an `ask` whose `request_id` already has a message
(re-emission after hook retry).

**Rendering** (`render.py`, pure functions returning `(text, rows)` where `rows` is a list of lists of
`(label, callback_data)`; `telegram.py` converts to `InlineKeyboardButton`):
- `notify/*`: `payload["text"]` verbatim, no keyboard.
- `ask/permission`: `payload["text"]` (already has title, summary, numbered choices). One row:
  `1 Allow`, `2 Always`, `3 Deny` → callback `ccb:<request_id>:0:<choice index>`.
- `ask/question`, one message **per question** (Telegram keyboards are per message; several questions =
  several messages, sent in order). Text: `❓ [name] (q/N) header: question` + numbered options with
  descriptions (button labels truncate, so the full text lives in the body). Keyboard: one button per option
  (`<index> <label>` truncated to 32 chars, ≤ 4 per row), plus `✏️ Other` when `allow_free_text`. Multi-select:
  buttons toggle (`✅` prefix), plus a `Submit` button; callback data `ccb:<rid>:<q>:<opt>`, `…:<q>:submit`,
  `…:<q>:other`. `callback_data` ≤ 64 bytes — assert in tests (`request_id` is 24 chars).
- Store per-request UI state in memory: `{request_id: {name, questions, message_ids{q: mid}, selected{q: set},
  answered{q: str}}}`; persist nothing (a gateway restart drops it; the human then answers by text — that is
  acceptable and documented).

**Callback flow** (`CallbackQueryHandler(pattern=r"^ccb:")`):
1. `await query.answer()` first. Parse data; unknown/expired request → `query.answer("This request is no longer pending")`
   and edit the message to strike the keyboard.
2. Authorization: `adapter._is_callback_user_authorized(str(query.from_user.id), chat_id=…, chat_type=…,
   thread_id=…, user_name=…)` via `getattr`; on `False` → `query.answer("⛔ not authorized")`, no action. If the
   method does not exist, allow only when `query.message.chat_id == target chat_id`.
3. Single-select option → record answer for that question. Multi-select option → toggle and re-render the
   keyboard (`edit_message_reply_markup`). `submit` → record the joined selection (`1,3`). `other` → edit the
   message to `…\n✏️ Reply to this message with your answer` and register the message id in
   `awaiting_text{message_id: (request_id, q)}`.
4. When every question of the request has an answer → `runner.answer(name, q_replies)` (permission: single
   reply `yes|always|no`). On success edit each question message: keyboard removed, `✔ <answer>` appended. On
   `ccb` error edit the message with the error text (e.g. `no pending request` — someone answered in the
   terminal) and drop the state.

**Free text** (`MessageHandler(filters.REPLY & filters.TEXT, …)` registered by the factory so it precedes the
core text handler): handle only if `update.message.reply_to_message.message_id in awaiting_text` **and** the
user is authorized (same check); then treat the text as the answer for that question and continue the flow
above. Any other message must fall through untouched: return without consuming it — verify with a test that
the handler's filter does not match a non-reply message. Document the second free-text path: with the skill
installed, the human may simply write the answer in the chat and the agent relays it (`cc_answer`).

**Message hygiene**: keep total text ≤ 3900 chars per message (split questions across messages; truncate
`summary` with `…`), escape nothing (send with `parse_mode=None`).

### 4.4 Tools (`tools.py`, toolset `ccb`)

| Tool | Parameters | Behaviour |
|---|---|---|
| `cc_start` | `name` (slug), `cwd` (optional → `default_cwd`), `prompt` (optional), `claude_args` (optional string) | `ccb start … --json`; returns the state JSON. Description must say: *after this call your turn is over; events arrive as new messages; do not poll.* |
| `cc_answer` | `name`, `reply` (string as the human typed it) **or** `answers` (object `{"1": "2", "2": "1,3"}`), `message` (deny reason) | maps to `ccb answer` / `--q`; returns ccb's stdout or the error text. Description: *only relay a reply the human wrote; never choose for them.* |
| `cc_send` | `name`, `text` | `ccb send`. |
| `cc_status` | `name` (optional) | `ccb status [--json]`; returns compact JSON (`name, status, pending{id,kind,summary}, last_message[:500]`). |

Handlers are sync (`is_async=False`), signature `(args: dict, **kw) -> str`, return JSON strings, never raise.
`check_fn` returns False (tools hidden) when `ccb.py` or `tmux` cannot be found.

### 4.5 `/ccb` command (`command.py`)

`/ccb` → `ccb list` output; `/ccb status <name>`; `/ccb stop <name>`; `/ccb start <name> <cwd> [prompt…]`;
`/ccb answer <name> <reply…>`; `/ccb help`. Plain text replies (≤ 3500 chars). The handler has no chat
context; that is fine for these operations.

### 4.6 System prompt section

≤ 900 chars, English, no markdown headers. Content: what `cc_*` tools are for; the four hard rules; "a human
message that arrives while a session has `pending` is the answer — call `cc_answer` and confirm in one line".

## 7. Decisions already made (do not re-litigate)

- Plugin at the **repo root**, so a single `hermes plugins install owner/repo` ships `ccb.py` along; the
  `skills/` tree keeps working as a Hermes skills tap.
- One Telegram message per question; UI state in memory only; free text via reply-to-message.
